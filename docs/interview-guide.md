# 项目讲解与演示提纲

本页帮助按实现顺序讲清项目，不涉及比赛成绩、成员分工或没有运行过的对比实验。

## 项目概述

这个项目把游戏数据分析问题转成 StarRocks SQL。难点除了生成合法语法，还包括确定统计人群、时间口径和跨表关联。实现中先按题目表列表构造上下文，再注入业务知识和逐题逻辑指引。LangGraph 管理工具调用与提交过程，执行错误交回 Agent 修正，已知错误结果由拦截器识别，最终 SQL 会重新查询数据库后保存。

公开仓库附独立自造数据，既可以执行已有 SQL 验证环境，也可以让模型重新解题；还提供固定工具序列的闭环回放，帮助观察拦截器的实际行为。

## 建议的演示顺序

1. 在[方案设计](solution.md)说明有限参考样本和业务口径问题，再打开[架构说明](architecture.md)定位实现。
2. 执行 `python main.py --cache_only` 与 `python scripts/verify_demo.py`，确认数据库和输出格式。
3. 执行 `python scripts/replay_demo.py`，展示空结果被拦截、修正规划和最终重执行。明确这一步使用预设工具调用。
4. 有可用 API 配置时，再运行 `--ignore_cache --rerun_ids sql_1`，展示真实模型工具调用。

## 常见追问

### 为什么选择 Agent，而没有直接做 SFT？

原始资料记录参考 SQL 数量有限，业务规则又需要从执行中反复确认。方案选择先利用推理时上下文与数据库反馈，便于修改业务约束。仓库没有 SFT 训练实现，也没有证明该路线优于 SFT 的实验。

### 这是 RAG 或多 Agent 系统吗？

目前按题目提供的 `table_list` 查找 Schema，按 `sql_id` 查找指引，没有向量索引。多个工具由同一个 Agent 调用，没有多个独立 Agent 之间的协商协议。

### 为什么 SQL 能执行还需要拦截？

错误日期、错误人群或错误关联方式可能产生合法 SQL。执行反馈只能说明数据库是否接受查询；已知错误结果黑名单可以补充识别部分业务错误，但不保证覆盖所有错误。

### 先侦察如何保证？

当前依赖 Prompt 协议，图没有单独验证模型是否完成侦察。若要严格保证，需要增加状态字段和提交前检查；公开版本没有声称已经实现。

### 第 5 次失败后会发生什么？

第 5 次返回更换思路的提示，第 6 次仍命中时历史实现会放行。最终重执行保证输出来自当前 SQL，不保证业务结果正确。

### 增加并发能否让 SQL 同时执行？

当前数据库调用受 `DB_LOCK` 保护，主要并发的是模型请求。没有吞吐量实验时，不把线程数直接换算成加速倍数。

### 如何避免把答案缓存当成模型效果？

分开运行缓存回归、模型重新生成与未知任务评估。当前公开演示只证明功能闭环；从已有答案归纳的逐题指引，也应在泛化评估中单独说明。

### 下一步优先改什么？

可以从严格的提交验证和知识版本管理开始，再建立与既有答案隔离的评估集。应先明确目标、控制变量和实际测量方式，再报告改进结果。
